# Tars

제품 용어와 세션 동작의 기준은 [TARS 문서](docs/README.md)에 정리합니다. **세션은 같은 대화 문맥을 유지하는 단위**이고, 한 번의 AI 처리는 **실행**입니다.


개인용 AI 팀 운영 웹서비스. 부서와 AI 팀원을 구성하고, 팀장과 협의한 내용을 문서와 작업으로 연결합니다.

현재 구현은 React + Vite 프런트엔드와 Fastify 백엔드로 분리되어 있습니다. 데이터는 SQLite에 저장하며, Codex 실행은 로컬 App Server, Claude 실행은 CLI에 연결합니다. 로그인은 없고 두 서버는 `0.0.0.0`에 바인딩합니다.

## 시작하기

필요 환경: Linux, Node.js 22.13 이상, npm, Python 3.8 이상. Git worktree를 사용하려면 Git과 최소 하나의 커밋이 있는 소스 저장소가 필요합니다.

```bash
cd /home/hjjin/tars
npm install --ignore-scripts
./run
```

`run` 화면에서 `1`을 입력하고 Enter를 누르면 백엔드와 프런트엔드를 시작합니다. 이번 구현 작업에서 의존성은 설치했으므로 현재 체크아웃에서는 다시 설치할 필요가 없습니다.

| 주소 | 용도 |
| --- | --- |
| `http://<서버 IP>:5173` | 다른 PC에서 접속하는 웹 화면 |
| `http://<서버 IP>:3001/health` | 백엔드 준비 상태 |
| `http://127.0.0.1:5173` | 서버 자신에서 접속하는 웹 화면 |

`run` 화면의 WEB·API 줄에는 접속할 수 있는 서버 주소를 표시합니다. 상태 확인용 HTTP 요청과 프런트엔드의 백엔드 프록시는 계속 `127.0.0.1`을 사용합니다. 공통 바인딩과 포트는 `network.config.mjs`에 정의합니다.

브라우저의 요청 호스트를 프록시에서 보존하므로 서버 IP로 접속해도 API와 SSE를 동일 출처로 사용할 수 있도록 구성했습니다. 기본적으로 서버의 네트워크 인터페이스 주소와 호스트 이름을 허용합니다. 별도 DNS 이름이나 NAT 외부 주소가 필요하면 `TARS_ALLOWED_HOSTS=tars.example.internal,203.0.113.10 ./run`처럼 추가할 수 있습니다.

```bash
./run status
./run stop
./run restart
./run restart backend
./run rebuild
./run rebuild frontend
./run logs backend
./run --plain status
```

CLI 화면은 `~/axtest/run.sh`와 해당 프로젝트의 `backend/axtest/console.py`를 참고했습니다. 그라데이션 로고, 서버별 상태·PID·가동 시간·HTTP 응답, WEB·API 접속 주소, 최근 로그, 고정된 하단 상태 줄을 제공합니다. 상태 수집은 2초 간격이며 입력 줄과 애니메이션은 독립적으로 갱신합니다. 창이 작으면 로고를 생략하고 화면 폭에 맞춰 한글도 잘라 표시합니다.

대화형 명령은 `/start`, `/stop`, `/restart`, `/rebuild`, `/logs`, `/status`, `/help`입니다. `/restart backend`, `/logs frontend`처럼 개별 서버를 지정할 수 있고, 번호 메뉴 `6`으로도 리빌드할 수 있습니다. ↑·↓는 명령 이력, Ctrl+U는 입력 지우기입니다. `TARS_PLAIN=1 ./run` 또는 `./run --plain`은 ANSI 화면 없이 상태를 출력합니다. 리다이렉트 시에도 평문으로 표시합니다.

`./run rebuild`는 각 서버 디렉토리에서 `npm run build`를 실행합니다. 현재 프런트엔드는 `frontend/dist`를 갱신하고, 백엔드는 build 스크립트가 없어 생략합니다. 빌드와 서버 재시작은 별도 명령이며, `start`는 계속 개발 서버를 실행합니다. 빌드 출력은 `.tars-run/<서버>.log`에 저장하며 `/logs frontend`로 확인할 수 있습니다. 빌드 실패는 오류로 표시하고 CLI는 종료 코드 1을 반환합니다.

대화형 화면에서 `q`를 누르면 콘솔만 닫고 서버는 유지합니다. 서버 중지 시 백엔드는 자신이 시작한 AI 실행도 중지하도록 구성했습니다. 준비 중이거나 실행 중이던 작업은 다음 서버 시작 시 중단 상태로 정리하고, 자동 재시작하지 않습니다.

`npm run dev:backend`, `npm run dev:frontend`로 각각 실행할 수도 있습니다. `run` 밖에서 시작한 프로세스는 `run`의 관리 대상이 아닙니다.

## 첫 작업 흐름

1. 첫 화면 **수신함**에서 대기 항목을 확인하고 **대화**에서 TARS·팀장에게 업무를 지시합니다. 대화 자체로 업무가 생성되지는 않습니다. 질문·현황 조회는 대화로 답합니다.
2. 목표와 범위를 정리한 팀장·CEO가 업무를 등록합니다. 등록한 업무 ID에 요구사항·설계 사양과 하위 작업을 연결하고 담당 AI에게 맡깁니다. 코드 작업이 필요한 부서는 **AI 조직 → 부서 설정 → 기본 소스 프로젝트**에서 등록된 소스 프로젝트를 할당합니다. 팀장과 협의하거나 결과 보고를 요청할 때 해당 부서의 기본 프로젝트가 자동 적용됩니다.
3. **업무 흐름**에서 등록 주체, 업무별 문서, 하위 작업, 시간순 수행·검토 기록과 최종 보고서 본문을 확인합니다. **AI 작업 기록**은 하위 작업의 상세 보기입니다.
4. 작업 결과는 별도 검토를 거쳐 완료 여부가 결정됩니다. Git 작업의 원본 반영은 별도 상태로 표시됩니다.

팀장·CEO가 목표·범위와 업무 완료 기준을 제출하면 사용자 승인 대기로 전환합니다. 기본 승인은 이 범위에 적용되며, 승인 뒤의 TASK 세분화·담당자·문서 문구 변경은 재승인을 요구하지 않습니다. 업무별 **TASK 목록도 승인**을 켜면 작업 목록 변경도 승인 대상이 됩니다. 업무 흐름 또는 작업 기록에서 승인하면 원래 담당 AI가 이어서 처리하고, 승인된 범위의 담당자·완료 기준이 있는 초안은 실행 대기열에 등록합니다. 추가 의견을 보내면 협의안을 보완해 새 버전으로 다시 확인받습니다. 설계 사양을 별도 AI가 검토하는 흐름은 후속 범위입니다. 동일 AI의 실행은 한 번에 하나만 진행합니다. 여러 세션의 메시지는 대기열에서 처리합니다. 기본 동시 실행 한도는 2개이며, 최대 8개까지 설정할 수 있습니다.

## 화면과 구현 범위

| 화면 | 구현 내용 |
| --- | --- |
| 수신함 | 기본 첫 화면. 협의안·결과 승인, 차단 재시도·범위 변경·중단, AI 질문과 대기 사유 |
| 대화 | TARS·팀장·팀원 공통 대화, 승인 카드, 실행 중 추가 지시와 자동 작업 중 메시지 대기열 |
| 업무 | 업무 흐름과 TASK 기록 탭, 범위·완료 기준·승인 정책, 수행·검토·보고 |
| 세션 | 문맥을 공유하는 세션 목록, 새 세션·기존 세션 재개, 세션별 대화와 실행 기록 |
| 조직 | 부서·AI 구성 및 소스 프로젝트 탭, 종류별 모델·추론 설정, 전체 작업 모니터링 링크 |
| 자료 | 문서·스킬 편집, 문서 버전과 공통 지침 |
| 사용량 | Codex·codex2·Claude 계정별 플랜과 사용 한도 |
| 설정 및 연결 | CLI 상태, 실행 승인 모드, 동시 실행·시간 제한, 메뉴 순서 |

실행 상태는 SSE로 전달하고 연결 복구를 위해 주기적으로 상태를 재조회합니다. 샘플 조직이나 가짜 실행·사용량을 채워 넣지 않습니다. 최초 실행에는 고정 CEO **TARS**와 공통 작업 지침을 생성합니다.

워크스페이스는 상단 통계 위젯 없이 **CEO와 모든 부서의 작업 모니터링**을 중심으로 구성합니다. 작업 수·부서 수를 잘라 표시하지 않으며, 팀원의 작업뿐 아니라 CEO 대화·총괄 보고와 팀장의 협의·결과 보고 실행도 함께 표시합니다. 담당자, 현재 상태·진행 메시지, 경과 시간, 선행 작업·담당자·실행 한도에 따른 대기 사유를 확인하고 **실행 보기 / 실행 기록**으로 기존 CLI 창을 엽니다. 조직·상태 필터와 작업·팀원·프로젝트 검색을 제공하며, 기본적으로 미완료 작업과 현재 실행·최근 실패를 표시합니다. **완료·취소·이전 실행 포함**을 선택하면 과거 기록도 확인할 수 있습니다. 이 화면 변경은 소스만 반영했으며 테스트·빌드·실행 검증은 수행하지 않았습니다.

**설정 및 연결 → 좌측 메뉴 순서**에서 손잡이를 드래그하거나 위·아래 버튼으로 메뉴를 옮기고 **순서 저장**을 누르면 좌측 메뉴에 적용됩니다. 손잡이에 키보드 초점을 둔 상태에서 위·아래 방향키로도 이동할 수 있습니다. **기본 순서**와 **변경 취소**를 지원하며, 저장 전에는 좌측 메뉴를 바꾸지 않습니다. 순서는 서버 설정에 저장해 새로고침·서버 재시작·다른 브라우저 접속 후에도 유지합니다. 설정 및 연결은 하단에 고정하고, 일반 좌측 메뉴에서는 드래그 편집을 제공하지 않습니다. 새 메뉴가 추가되면 저장된 순서 뒤에 자동으로 붙습니다. 이 기능의 저장 API를 적용하려면 실행 중인 백엔드를 재시작해야 합니다.

기본 테마는 검정 바탕·초록색 강조·빨간색 경고의 다크 모드입니다. 매트릭스의 터미널과 우주선 계기판을 참고해 선, 격자, 각진 패널과 숫자용 고정폭 글꼴을 사용합니다. 상단 해/달 버튼으로 기존 라이트 모드와 전환할 수 있고, 선택은 브라우저의 `tars:theme`에 저장됩니다. 첫 화면이 그려지기 전에 저장된 테마를 적용하며 다른 탭의 선택도 동기화합니다. 다크 모드는 작업 보드, 협의, 문서·입력창, 모달, 로그, 계정 주간 한도에 공통 적용합니다.

## 조직도와 모델 선택

조직도의 **부서 추가**, **팀장 추가**, **팀원 추가** 버튼으로 해당 위치에 AI를 구성합니다. 각 AI 카드에서 상태, 모델, 추론 깊이를 확인하고 **프로필 · 소속 설정**으로 이름·역할·소속을 변경합니다. 부서 설정에서는 연결된 AI·작업·문서·실행 기록이 없는 부서를 삭제할 수 있습니다. 부서별 팀장은 한 명이며, 실행 중인 AI는 실행을 중지한 뒤 수정할 수 있습니다. 미완료 담당 작업이 있는 팀원의 소속·역할 변경은 해당 작업을 먼저 정리해야 합니다. 부서를 접거나 필터로 하나만 볼 수 있고, 큰 조직도는 좌우로 스크롤합니다.

TARS와 팀장·팀원은 같은 모델 선택 UI를 사용합니다. 모델을 변경해도 선택한 추론 깊이는 자동 변경하지 않습니다. Codex가 지원 깊이 목록을 제공하면 해당 옵션을 표시하고, 현재 깊이가 새 모델에서 미지원이면 다른 깊이를 선택하도록 안내합니다. 목록에 없는 기존 모델 ID도 유지하며 **모델 ID 직접 입력**으로 설정할 수 있습니다.

모델 선택은 VS Code 참고 이미지처럼 추론 단계와 모델명을 위에 표시하고, 막대와 흰 손잡이로 깊이를 조절합니다. 게이지와 손잡이는 함께 부드럽게 이동하며, 높은 추론 단계일수록 파란색에서 보라색으로 바뀌고 작은 별이 나타납니다. 모션 감소 설정에서는 전환 애니메이션을 생략합니다. 모델명을 누르면 이름·ID를 검색할 수 있는 목록이 열립니다. 슬라이더는 방향키로 조절할 수 있고, 목록은 위·아래 방향키와 Enter로 선택하거나 Escape로 닫습니다. 좌측 번개 버튼은 모델을 유지하고 지원되는 가장 낮은 추론 단계로 전환하며, 우측 초기화 버튼은 추론 깊이를 CLI 기본 설정으로 되돌립니다.

- Codex: [공식 App Server `model/list`](https://learn.chatgpt.com/docs/app-server#list-models-modellist)에서 설치된 CLI가 제공하는 모델과 지원 추론 깊이를 가져옵니다. 설정 화면에서만 조회하며 AI 작업·대화 세션을 시작하지 않습니다. 서버는 성공 목록을 10분, 조회 실패를 1분 캐시하고 동시 요청을 합칩니다.
- Claude: [공식 모델 별칭](https://code.claude.com/docs/en/model-config#model-aliases)인 Sonnet·Opus·Haiku를 제공합니다. 구체적인 버전과 사용 가능 여부는 설치된 CLI·계정 설정을 따르며, Tars는 별칭 목록을 계정 권한 확인 결과로 표시하지 않습니다.
- 조회 실패나 CLI 미설치 시에도 기본 모델·직접 입력을 사용할 수 있습니다. 재조회는 캐시 기간을 따릅니다.

조직도·모델 선택의 테스트, 빌드 및 실행 검증은 수행하지 않았습니다. 새 모델 목록 API를 사용하려면 실행 중인 백엔드를 재시작해야 합니다.

## CEO TARS

TARS는 모든 부서 위에 있는 고정 CEO AI입니다. 백엔드 시작 시 한 번 생성되고, 이름·역할·부서 소속은 변경할 수 없습니다. 일반 팀원 생성에서 `TARS` 이름은 예약되어 있습니다. **TARS 설정**에서 Codex/Claude, 모델, 추론 수준과 추가 업무 지침을 설정합니다. 초기 설정은 Codex, CLI 기본 모델, High 추론입니다.

상황실의 각 AI 창에서 **새 세션**을 시작하거나 **세션 선택**으로 이전 대화를 재개합니다. 같은 AI에게 여러 세션이 있을 수 있고, 세션별 대화 문맥과 실행 기록을 분리합니다. 패널 크기·위치와 선택한 AI는 브라우저에 보관하지만 세션 선택은 창을 떠난 뒤 자동 복원하지 않습니다.

대화창에는 선택한 세션의 기록만 시간순으로 표시합니다. 위로 스크롤하면 이전 기록을 30개씩 추가하며 읽던 위치를 유지합니다. Enter로 전송하고 Shift+Enter로 줄바꿈합니다. 응답이 끝나도 같은 세션에서 후속 메시지를 보낼 수 있습니다. Codex 실행 중에는 현재 턴에 추가 지시를 보내고, Claude 추가 지시는 현재 응답 뒤 처리합니다. 해당 AI가 다른 실행 중이면 메시지에 세션 ID를 저장해 대기열에서 순서대로 처리합니다. **세션 닫기**는 기록을 보존하며 진행 중인 서버 실행은 계속됩니다. 실행을 멈추려면 **중지**를 사용합니다.

대화창 상단의 **새 대화** 버튼 또는 `/clear`로 해당 AI의 대화 문맥을 초기화합니다. 진행 중인 응답이나 작업이 끝난 뒤 사용할 수 있습니다. 이전 기록은 화면에 보존하며, 초기화 후에는 이전 대화의 thread와 과거 기록 발췌를 자동으로 이어받지 않습니다. `/stop`은 해당 AI의 현재 응답을 중지하고 `/help`는 입력 도움말을 표시합니다. 개별 실행의 명령·도구 출력은 각 응답의 **실행 기록**에서 확인합니다. 기존 작업·승인·결과 기록은 그대로 보관하며, 대화만으로 업무를 자동 생성하지 않습니다.

**TARS 상황실**(`/ceo`)과 **프로젝트 관리**(`/projects`)는 별도 메뉴입니다. 프로젝트 등록·소스 경로, 진행 현황, 분석 보고서 요청과 기존 보고 기록은 프로젝트 관리에서 확인합니다.

프로젝트 관리 화면은 등록된 작업의 상태를 집계하여 프로젝트별 진행·검토·차단·완료율과 담당 부서·팀장을 보여줍니다. 완료율은 취소 작업을 제외하며, 등록 작업의 완료를 배포나 실제 검증 완료로 간주하지 않습니다. 프로젝트 미지정 작업도 별도 표시합니다. 프로젝트의 **작업 보기**를 누르면 해당 프로젝트로 필터된 작업 보드로 이동합니다.

현황 조회 자체는 AI를 호출하지 않습니다. **현황 분석 요청**을 누르면 TARS가 전체 또는 선택한 프로젝트의 현황과 필요한 부서 보고를 읽고, 차단 원인·담당 부서·다음 우선순위를 보고합니다. 이 분석은 기존 실행 한도와 중지 기능을 따르는 별도 세션입니다. 결과는 공통 문서의 보고서로 저장되며, 요청 범위에 포함된 후속 배정·실행과 조직 변경도 수행할 수 있습니다.

TARS의 개인 자료는 `.tars-data/executive/tars/`에 보관합니다. 다른 AI와 동일한 공통 지침·스킬 연결과 `AGENTS.md`/`CLAUDE.md`를 사용합니다. 분석 요청마다 `project-status.json`에 전체 요약을 만들고, 프롬프트에는 작업 개수와 파일 경로만 전달합니다. 필요한 나머지 자료는 해당 파일과 보고서에서 선택해 읽도록 합니다. 기존 대화 전체나 개별 토큰 통계는 전달하지 않습니다.

AI별 대화는 백엔드 회귀 테스트와 제공자 대역 테스트, 프론트엔드 빌드, Chromium에서 이름 선택·이력 스크롤·후속 전송·중지·새로고침·모바일 표시를 검증했습니다. 실제 Codex·Claude 모델 응답을 호출한 검증과는 구분합니다. 새 대화 API 반영에는 백엔드 재시작이 필요합니다.

## AI 대화와 실행 기록

대화 입력창에서 `/`를 입력하면 실행 가능한 명령과 설명이 표시됩니다. `/clear`·`/new`는 이전 기록을 보존하고 새 문맥을 만들며, `/stop`은 응답 중지, `/model`·`/reasoning`은 AI 설정, `/status`는 최근 실행 기록, `/help`는 입력 도움말을 엽니다. Codex 대화의 `$`와 `/skills`는 선택한 계정·프로젝트·실행 경로에서 발견한 스킬을 검색합니다. ↑↓로 이동하고 Tab·Enter 또는 클릭으로 입력을 완성한 뒤, Enter를 다시 눌러 전송합니다. Shift+Enter는 줄바꿈, Esc는 목록 닫기입니다. 실행 기록의 추가 지시 입력창에도 `$`와 `/stop`을 지원합니다.

스킬 목록은 `POST /api/members/:id/chat/skills`에서 기존 SQLite 지침 생성기로 범위를 준비하고 Codex `skills/list`를 조회합니다. 실행 중인 세션은 원래 작업 경로를 사용합니다. 비활성 스킬은 제외하고 중복 이름·조회 오류는 화면에 표시하며, 이 조회는 모델 실행을 시작하지 않습니다. 현재 사용자 메시지의 명시적 `$이름`만 Codex `skill` 입력으로 전달하고 과거 대화나 코드 예제의 언급은 제외합니다. 명령은 TARS에서 연결한 기능만 제안하며, CLI·VS Code 확장의 모든 명령을 그대로 실행하는 기능은 아닙니다. 명령 동작 참고: [Codex 명령 문서](https://developers.openai.com/codex/cli/slash-commands/).

**AI와 대화**, 상황실의 AI 창, 조직도의 **대화하기**, **팀장과 협의**는 해당 AI의 세션 선택과 입력창을 제공합니다. `/sessions?member=<AI ID>`는 새 문맥으로 시작하는 창을 열고, `/sessions?conversation=<세션 ID>`는 지정한 세션을 엽니다. 이전 `?session=<실행 ID>` 링크는 그 실행이 속한 세션으로 연결합니다. `/sessions`는 세션 목록, `/runs`는 업무·작업별 전체 실행 기록입니다.

사용자 대화는 `POST /api/members/:id/chat`으로 전송합니다. 실행 기록은 메시지마다 따로 저장하지만 대화의 식별자는 AI에 귀속됩니다. 업무 등록으로 `requestId`가 생겨도 대화를 분리하지 않습니다. AI는 기존 업무의 승인·배정 권한을 그대로 따릅니다.

각 응답의 **실행 기록**에서는 실행별 SSE로 명령·도구 출력과 공개 응답을 증분 수신합니다. 처음에는 최근 48 KiB를 표시하며 **이전 로그**로 과거 바이트 구간을 조회합니다. 기록은 실행별 `terminal.log`에 최대 64 MiB를 보존하고, 단일 출력 12,000자 절단은 제거했습니다. 내부 추론·사용량·인증 JSON은 기록하지 않습니다. 상세 출력이 없는 과거 실행은 기존 요약과 응답을 표시합니다.

종료한 실행의 **이어서 실행**은 원래 제공사 세션 ID와 작업 경로로 새 실행 기록을 만듭니다. 현재 TASK의 중단·차단 작업은 승인 상태를 확인해 재개하며, 완료한 검토·보고는 대화로 이어서 이전 결과를 덮어쓰지 않습니다. **CLI 인계**는 계정에 맞는 재개 명령을 제공하고 AI를 잠급니다. 사용자는 CLI를 종료한 뒤 인계를 해제해야 합니다. CLI 안의 직접 작업은 TARS의 TASK 결과 제출·검토를 자동 수행하지 않습니다.

## AI 실행과 문맥 관리

- CLI 설치 여부는 실행 파일 경로로 확인합니다. 인증 유효성이나 모델 접근 권한은 실제 호출 전까지 확인한 것으로 표시하지 않습니다.
- 백엔드가 실행되는 사용자 계정의 CLI 인증과 설정을 사용하며, 인증 파일을 웹 화면에 노출하거나 데이터베이스에 복사하지 않습니다.
- 필요하면 `TARS_CODEX_BIN`, `TARS_CODEX2_BIN`, `TARS_CLAUDE_BIN` 환경 변수에 실행 파일 절대 경로를 지정할 수 있습니다. PATH에서 찾지 못하면 `~/.local/bin`과 `~/bin`도 확인합니다.
- Codex는 계정별 `codex app-server` / `codex2 app-server` 프로세스와 stdio JSON-RPC 연결을 유지합니다. `initialize` 후 `thread/start` 또는 `thread/resume`, `turn/start`를 사용합니다. 역할별 읽기·쓰기 범위를 유지하며, 검토 모드에서는 `untrusted` 승인 정책을 사용합니다. 서버의 질문·명령·파일 변경·추가 권한 요청은 사용자 응답까지 보관하고 원래 요청 ID에 응답합니다.
- Claude는 고정 버전의 `@anthropic-ai/claude-agent-sdk`에서 설치된 Claude Code 실행 파일을 사용합니다. `claude_code` 기본 프롬프트와 user/project/local 설정, 기존 로그인 환경, 명시적 세션 재개를 유지합니다. `canUseTool`로 질문·실행 승인을, `onElicitation`으로 MCP 입력 요청을 전달합니다. 입력 스트림을 유지하므로 추가 지시는 현재 응답 후 같은 대화에서 순서대로 처리합니다. 도구·샌드박스 범위는 역할별 실행 정책을 따릅니다.
- 제공 도구의 하위 에이전트도 사용할 수 있습니다. TARS에 등록된 AI의 실행은 기존 작업 대기열·동시 실행 한도·실행 시간 제한을 따르며, CLI 자체 하위 에이전트는 별도 TARS 구성원으로 자동 등록되지 않습니다.
- 직접 대화는 선택한 세션의 Codex thread 또는 Claude session을 재개합니다. 실행 ID와 업무 ID가 바뀌거나 모델·추론 깊이·지침이 바뀌어도 같은 제공사 문맥을 유지하고 현재 설정을 적용합니다. 제공사·계정·프로젝트·작업 경로는 세션의 재개 범위이며, 다르면 오류를 표시합니다.
- 실패·중단된 턴 뒤에도 제공사 ID가 있으면 같은 세션을 재개합니다. 재개 실패 시 새 문맥으로 자동 전환하지 않습니다. 새 세션은 이전 대화 메시지를 가져오지 않습니다. SQLite에서 같은 AI·세션의 이력만 `.tars-data/conversations/<세션 ID>.md`로 생성하고, 최근 최대 8건·24,000자 발췌와 전체 기록 경로를 전달합니다. 재개 시에는 이전 실행 이후 기록만 추가합니다. 파일은 과거 문맥이며 자동 재실행 지시가 아닙니다.
- Codex 요청에는 공용·개인 지침 본문이나 TARS가 만든 스킬 목록을 붙이지 않습니다. 작업 디렉토리에서 `AGENTS.md`와 `.agents/skills/`를 탐색하도록 연결합니다. 재개 시 이전 대화 전체와 인계 요약은 반복하지 않고, 관련 문서 발췌는 변경됐을 때 전달합니다. 프로젝트 현황 파일과 개수 요약, 현재 요청은 매번 갱신합니다. 현황 JSON 전체는 반복 주입하지 않습니다. 새 대화에는 기존 기록의 제한된 요약을 전달할 수 있습니다. 자동 로딩된 지침도 모델 문맥에 포함됩니다.
- Codex 자동 적용 지침의 상한은 전역 지침을 포함해 32 KiB입니다. 합계 16 KiB 초과, 개별 파일 8 KiB 초과, 동일 본문 반복은 로딩 보고서에 표시합니다. 상한 초과·필수 지침 누락·스킬 로딩 오류는 턴 시작 전에 차단합니다. 바이트는 UTF-8 본문과 구분자 기준이며 토큰 수가 아닙니다. Claude에도 TARS가 전달하는 지침 본문의 32 KiB 상한을 적용하며, 지침을 중간에서 잘라 전달하지 않습니다. Claude 자체의 전역 지침 로딩 크기는 집계하지 않습니다. 관련 문서 발췌에는 기존 길이 제한과 원문 경로 안내를 유지합니다.
- 팀장 결과 보고에는 최근 24개 작업의 요약을 전달하며, 대상이 더 많으면 보고 범위를 명시하도록 합니다.
- 기본 시간 제한은 실행당 30분입니다. Codex 공개 응답 누적 및 RPC 메시지당 제한은 8 MiB, Claude 최종 공개 응답은 최근 80,000자를 보존하고 전체 공개 출력은 로그에서 확인합니다. Tars는 실패한 작업을 자동 재실행하지 않으며 Codex 자체의 연결 복구 이벤트는 표시합니다.

### 역할·모델과 실행 준비

관리자 대화·협의·검토·보고는 읽기 전용, 팀원 작업은 작업 폴더 쓰기로 실행합니다. 사용자가 업무의 **관리자 직접 구현**을 켜고 해당 범위를 승인한 경우에만 관리자에게 작업·연결된 소스 경로 쓰기를 허용합니다. AI 프로필에서 대화·설계·작업·검토·보고별 모델과 추론 깊이를 지정할 수 있으며, 미지정 값은 기본 프로필을 따릅니다. 보완 재검토는 호환되는 이전 검토 thread를 재사용합니다.

Claude는 샌드박스를 사용할 수 없으면 실행을 실패시킵니다. Linux에서 `bwrap`, `socat`이 없다면 `scripts/install-claude-sandbox.sh`로 TARS 내부 `.tars-run/sandbox`에 설치할 수 있습니다. 시스템 패키지나 사용자 CLI 설정은 수정하지 않습니다. 읽기 전용 Bash는 각 명령을 원래 작업 경로에서 시작하고 명령의 종료 코드를 그대로 반환합니다. `cd`는 해당 명령 안에서만 적용됩니다.

팀원 도구 `tars_log_progress`, `tars_block`은 현재 담당 TASK에 기록을 남기고, `tars_ask`는 입력 대기로 전환해 수신함의 사용자 답변을 기다립니다. 입력 대기는 실행 제한 시간에서 제외됩니다. 양쪽 제공사 모두 TARS MCP 도구 목록을 확인한 실행만 시작하며 실행 토큰은 MCP 환경으로 전달합니다.

### App Server 실행 제어

- 일반적인 중지와 시간 제한은 해당 thread/turn에 `turn/interrupt`를 보냅니다. 같은 계정의 다른 AI는 계속 실행할 수 있습니다. 추가 지시는 `turn/steer`와 `expectedTurnId`를 사용하며 실행당 최대 20회입니다.
- RPC 응답을 잃거나 턴 중지를 확인하지 못하면 실행 상태를 추측하지 않고 해당 계정 연결을 종료합니다. 이 경우 같은 계정의 진행 중인 세션도 실패 처리될 수 있습니다. 작업을 자동으로 다시 제출하지 않습니다. 다음 사용자 요청에서 새 연결을 만듭니다.
- 서버 재시작 시 Tars가 저장한 PID와 프로세스 소유 표식을 확인해 남은 실행 프로세스를 정리합니다. 실행 중이던 작업은 중단 상태로 남기고, 성공했던 대화는 다음 요청에서 저장된 thread로 이어갑니다. 별도의 App Server 네트워크 포트는 열지 않습니다.
- 모델 목록·계정 한도 조회는 기존의 짧은 메타데이터 연결을 유지합니다. 작업 실행용 연결은 긴 세션을 지원하며 조회 연결의 15초 제한을 공유하지 않습니다.
- 소스 전환 후 `./run restart backend`로 적용합니다. CLI 업데이트 후 `npm run check:ai`로 Codex의 질문·승인 응답 스키마와 양쪽 CLI 초기화·모델 조회를 확인할 수 있습니다. 이 검사는 모델 턴을 실행하지 않으며, 실제 모델·도구 실행 성공을 보증하지 않습니다.

CEO·팀장·팀원 모두 `tars_get_state`, `tars_register_work`, `tars_create_department`, `tars_create_member`, `tars_api` MCP 도구를 사용합니다. 기존 관리 API를 호출하므로 입력 검증·문서 버전·상태 이력·파일 생성이 웹 화면과 동일하게 처리됩니다. 작업 실행·검토·통합은 각 API의 상태 조건을 따릅니다. 도구 응답을 잃은 변경 요청은 자동 재시도하지 않으며, 상태를 재조회해 결과를 확인합니다.

`tars_get_state`는 기본 20개(최대 100개)씩 목록 요약과 전체 개수를 반환합니다. `collection`, `limit`, `offset`으로 범위를 좁히고, 문서 본문·실행 결과·승인 사본은 `collection`과 `id`로 한 건씩 조회합니다. 변경 API의 반환값으로 저장 결과를 확인하며 응답이 불확실할 때만 재조회합니다. 실행 중 담당자 현황은 `tars_get_team_activity`를 사용합니다. 새 조회 API가 없는 이전 서버에는 읽기 전용 호환 처리를 적용합니다. 웹 `/api/state`도 목록 요약만 반환합니다. 본문은 `/api/records/:kind/:id`로 읽으며, 진행 메시지는 별도 SSE 이벤트로 갱신해 전체 상태를 다시 받지 않습니다.

실행 권한 정책은 TARS가 시작한 Codex·Claude 프로세스에만 적용합니다. 서버 OS 계정의 파일 접근 권한과 외부 서비스 인증·관리자 정책은 그대로 적용됩니다. 로그인·입력 정보가 필요한 요청을 임의로 채우지 않습니다. 권한 변경 후 백엔드를 재시작하면 다음 실행부터 적용됩니다.

개별 세션·팀원·작업의 토큰과 비용은 수집하거나 집계하지 않습니다. 기존에 저장된 사용량 기록은 삭제하지 않지만 화면과 상태 응답, 팀장 보고용 문맥에서 제외합니다.

### 실행 중 질문·승인과 파일 변경 검토

설정의 **AI 실행 승인**에서 자동 실행(기존 허용 범위) 또는 검토 모드를 선택합니다. 새 실행부터 적용하며, 질문은 두 모드 모두 대화창·실행 기록·확인할 일에서 답변할 수 있습니다. 사용자가 이미 허용한 범위와 CLI 설정에 따라 요청이 필요한 실행만 승인 카드로 표시합니다.

- 질문은 선택지·직접 입력, 복수 선택, 비공개 입력을 지원합니다. 명령·파일 수정·추가 권한 승인은 실행 내용과 범위를 함께 표시합니다. MCP의 입력 폼과 URL 확인도 같은 경로를 사용합니다.
- 사용자 응답 대기는 실행 제한 시간에서 제외합니다. 브라우저 새로고침 후 같은 요청에 답할 수 있고, 중복 응답은 거절합니다. 실행 중단·서버 재시작·공급자의 요청 해제 시 요청을 만료시킵니다. 종료된 프로세스에 답변을 재전송하지 않습니다. 승인 응답 API는 사용자 요청만 받습니다.
- Codex 추가 지시는 현재 턴에 반영하고, Claude 추가 지시는 현재 응답이 끝난 뒤 처리합니다. 질문의 답변은 추가 지시와 별도로 원래 요청에 반환합니다.
- 작업 상세의 **파일 변경 검토**는 worktree의 신규 파일을 포함한 변경을 보여줍니다. 검토한 패치 해시와 AI 결과 버전이 일치할 때만 사용자가 원본 반영을 승인할 수 있습니다. 실행 중·검토 후 변경·중복 적용은 거절하며, 승인 당시의 패치 바이트를 그대로 적용합니다. 커밋은 생성하지 않습니다. 기존 `/api/tasks/:id/integrate` 경로도 사용자 신원과 검토한 `hash`, `reportId`를 요구합니다.
- 실행 중 Codex diff는 해당 턴이 보고한 변경이며, 최종 작업 검토는 Git 작업 폴더의 실제 변경을 사용합니다. 디렉토리 복사·개인 작업 폴더는 기존 수동 통합 방식을 유지합니다.

프로토콜 변경 대응에는 공식 [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Claude 사용자 입력](https://code.claude.com/docs/en/agent-sdk/user-input), [Claude 스트리밍 입력](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode)을 사용합니다. 확장 UI의 모든 기능을 자동으로 상속하는 구조는 아니므로 SDK·CLI 업데이트 시 호환성 검사와 회귀 검사를 실행해야 합니다.

### Codex 계정 두 개 함께 사용하기

- **AI 조직 → 프로필 · 소속 설정 → Codex 실행 계정**에서 `codex` 또는 `codex2`를 선택합니다. 팀장과 CEO TARS도 같은 방식으로 설정합니다. 계정과 모델·추론 깊이는 별도 값이며, 기존 AI는 기본적으로 `codex`를 사용합니다.
- 실제 실행, 모델 목록 조회, 계정 사용량 조회 모두 선택한 명령을 실행합니다. `codex2`가 없거나 실패하면 오류를 표시하며 다른 계정으로 자동 대체하지 않습니다. 서로 다른 계정의 AI도 기존 전체 동시 실행 한도 안에서 함께 작업합니다.
- 현재 로컬 명령은 `/home/hjjin/bin/codex`와 `/home/hjjin/.local/bin/codex2`입니다. `codex2` 래퍼 소스는 `~/.codex-accounts/account2`를 자식 프로세스의 `CODEX_HOME`으로 지정합니다. Codex의 상태·설정 저장 위치는 [OpenAI Docs의 CODEX_HOME 설명](https://learn.chatgpt.com/docs/config-file/config-advanced)을 참고합니다. Tars는 기존 래퍼를 그대로 호출하며 인증 파일이나 계정 디렉토리를 복사·교체하지 않습니다.
- 조직도 카드와 TARS 대화창에 계정명을 표시합니다. 실행 시 선택한 계정을 세션에 저장하므로 이후 프로필을 바꿔도 과거 CLI 기록의 계정 표시는 유지됩니다. 설정 및 연결에서는 `codex`와 `codex2`의 설치 여부를 따로 표시합니다.
- 변경 적용에는 백엔드 재시작이 필요합니다. 명령 경로와 래퍼 소스만 확인했으며, 로그인 유효성·두 계정의 실제 동시 실행·계정별 모델 및 사용량 조회는 미검증입니다.

### 내 계정의 사용 한도

- 사용량 화면에서 서버 사용자의 Codex·Claude 로그인 계정 플랜과 주간 사용률, 잔여 비율, 초기화 시간을 확인합니다. Claude는 5시간 한도를 주간 한도 위에 별도 게이지로 표시합니다. Tars 외부에서 같은 계정으로 사용한 내용도 포함하는 제공사 기준 한도입니다.
- `codex`와 `codex2`는 별도 카드와 캐시로 플랜·주간 한도를 조회합니다. 한 계정의 오류나 미설치 상태를 다른 계정의 사용량으로 대체하지 않습니다.
- Codex는 [공식 App Server 계정 조회](https://learn.chatgpt.com/docs/app-server)의 `account/read`, `account/rateLimits/read`만 호출합니다. 기존 CLI 인증 및 `CODEX_HOME` 설정을 사용하며, AI 대화나 작업을 시작하지 않습니다. 응답에서 기간이 7일인 한도만 표시합니다. API 키 등 주간 구독 한도를 제공하지 않는 인증 방식은 조회 미지원으로 표시합니다.
- Claude는 `CLAUDE_CONFIG_DIR` 또는 `~/.claude`의 로그인 정보를 읽어 Claude Code가 사용하는 `https://api.anthropic.com/api/oauth/usage`에서 5시간 한도(`five_hour`)와 주간 한도(`seven_day` 및 모델별 항목)를 조회합니다. 각 한도의 사용률과 초기화 시각은 독립적으로 표시하며, 일부 한도가 누락되면 해당 게이지는 `—`로 표시합니다. Max 5x·20x 정보가 있으면 플랜에 함께 표시합니다. `CLAUDE_CODE_OAUTH_TOKEN`을 별도로 지정한 경우 해당 토큰을 우선하며, 다른 계정일 수 있으므로 파일의 플랜 정보는 사용하지 않습니다.
- Claude 조회 경로는 공개 API가 아닌 CLI 내부 인터페이스이므로 변경되거나 조회가 거절될 수 있습니다. 자동 로그인·인증 갱신은 수행하지 않습니다. 파일에 접근할 수 없거나 로그인이 만료된 경우 조회 불가 안내를 표시합니다.
- `/api/account-usage`는 화면을 열었을 때만 호출합니다. 화면이 보이는 동안 1분 간격으로 갱신하고 탭이 숨겨지거나 다른 화면으로 이동하면 추가 조회를 멈춥니다. 서버에서도 계정별 최소 1분 캐시와 중복 요청 합치기를 적용합니다. 새로고침 버튼도 이 간격을 따릅니다. Claude의 429 응답은 최소 5분과 `Retry-After`를 반영합니다.
- 조회 결과는 서버 메모리에만 보관합니다. 인증 토큰과 원본 응답은 웹 화면·DB·로그에 노출하지 않습니다. 한도 미제공·조회 실패·0% 사용을 구분하며, 5시간 한도나 토큰 수로 주간 한도를 추정하지 않습니다.

계정 조회 및 화면의 실제 실행 검증은 아직 수행하지 않았습니다.

연동 근거: [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Codex CLI 참조](https://developers.openai.com/codex/cli/reference), [Claude 비대화형 실행](https://code.claude.com/docs/en/headless), [Claude CLI 참조](https://code.claude.com/docs/en/cli-reference).

## 소스 분리와 통합

**Git worktree**는 등록한 저장소의 현재 `HEAD`에서 별도 작업 디렉토리를 만듭니다. 원본의 미커밋 변경은 자동으로 가져오지 않습니다. 선행 worktree 작업의 변경은 의존 순서대로 작업 디렉토리에 적용합니다. 선행 변경과 이번 작업의 변경은 별도 기준 트리로 구분하여 패치에 중복 포함하지 않습니다. 기준 트리를 기록할 때 Git 객체와 인덱스를 사용하지만 커밋이나 푸시는 하지 않습니다.

준비 과정에서 의존 작업의 패치 충돌이 발생하면 실행을 차단합니다. 팀원 실행 후 변경 사항은 결과 버전에 연결하고, 팀장 검토를 통과한 버전만 원본에 적용할 수 있습니다. 적용 전 `git apply --check`를 수행하도록 구현했습니다. **원본에 미커밋 변경이 있으면 적용을 중단합니다.** 패치 적용은 커밋을 만들지 않으므로, 연속 통합 시 원본 변경 정리는 사용자가 처리합니다.

**디렉토리 복사**는 Git이 없는 프로젝트를 위한 방식입니다. `node_modules`, `.git`, Tars 데이터, `dist`, `.env*`, 심볼릭 링크는 복사하지 않습니다. 복사 방식 결과의 자동 패치 통합은 지원하지 않습니다. 선행 코드 변경을 이어서 실행하려면 Git worktree를 사용하거나 변경을 원본에 정리한 뒤 새 작업으로 실행합니다.

프로젝트를 지정하지 않은 작업은 팀원의 개인 디렉토리에서 수행합니다.

```text
      workspaces/<task-id>/    # Codex의 격리된 소스; 기존 프로젝트 AGENTS.md 유지
        .agents/skills/tars-<id> -> 해당 범위의 공용 스킬 폴더
    workspaces/<task-id>/      # 소스 프로젝트가 없는 개인 작업
  workspaces/<task-id>/        # Claude 및 아직 이동하지 않은 기존 작업 공간
  conversations/<conversation-id>.md # SQLite에서 생성한 같은 AI·세션의 대화 문맥
  sessions/<session-id>/       # 실행 로그, 계획 결과 스키마
    user-feedback.json         # 승인 대상 사본, 원래 응답, 사용자 의견과 이전 실패 시도
    guidance.md                # 적용 경로·바이트·중복 경고와 발견된 스킬 (로딩 확인 후 생성)
  tasks/<task-id>/record.md     # DB에서 생성하는 작업별 통합 업무 기록
  tasks/<task-id>/reports/<report-id>/changes.patch # 제출 시점의 Git 변경 패치
  patches/<task-id>.patch
.tars-run/                    # 서버 프로세스 상태, 표준 출력 로그
```

문서와 프로필의 관리 원본은 SQLite이며 파일은 이를 반영한 실행용 자료입니다. 수정은 웹 화면 또는 에이전트의 TARS 관리 도구를 통해 같은 문서·조직 API로 수행합니다. 전체 공용 지침에는 부서·프로젝트가 지정되지 않은 지침만 포함합니다. 부서 지침은 같은 부서에, 프로젝트 지침과 스킬은 해당 AI의 부서·프로젝트 범위에 적용합니다. CEO·팀장·팀원의 개인 지침은 서로 상속하지 않습니다.

지침 문서의 **적용 방식**은 다음과 같이 구분합니다.

| 방식 | 시작 시 포함 | 용도 |
| --- | --- | --- |
| 항상 적용 | 본문 | 권한, 필수 제약, 짧은 공통 규칙 |
| 필요할 때 읽기 | 제목·읽는 조건·원문 경로·버전 | 특정 작업에만 필요한 상세 절차 |
| 스킬 | 도구가 탐색한 이름·설명 등 메타데이터 | 반복 작업의 절차·스크립트·참고 자료 |

새 지침의 기본은 **필요할 때 읽기**이며 읽는 조건을 반드시 입력합니다. 기존 문서에 적용 방식이 없으면 **항상 적용**을 유지합니다. 기존 긴 지침은 문서 편집에서 필요한 규칙과 상세 절차를 구분한 뒤 적용 방식을 변경합니다. TARS는 기존 규칙을 임의 요약하거나 자동으로 조건부 지침으로 바꾸지 않습니다. 적용 방식과 조건도 문서 버전 기록에 보존합니다.

항상 적용하는 등록 지침은 **같은 부서·프로젝트 범위에서 본문 전체가 같을 때만** 한 번 렌더링하며 마지막 항목의 위치를 유지합니다. 줄바꿈과 앞뒤 빈 공간만 정규화하며, 문장 일부나 의미가 비슷한 내용은 자동 삭제하지 않습니다. 서로 다른 범위의 같은 지침은 하위 범위가 중간 규칙을 다시 덮어쓸 수 있으므로 그대로 두고 로딩 보고서에 표시합니다. 개인 지침에는 역할 차이만 적고 상세 절차는 문서로 옮깁니다. 원본 문서는 보존합니다.

최대 권한 전환 시 수정되지 않은 초기 `팀 공통 작업 원칙`만 새 정책으로 갱신하며, 이전 본문은 문서 버전 이력에 보관합니다. 사용자가 편집한 문서와 개인 지침은 유지합니다. 생성된 `.tars-data` 지침을 직접 편집하지 않습니다.

계정 전역 파일과 소스 프로젝트의 AGENTS.md는 TARS가 수정하거나 중복 제거하지 않습니다. App Server가 반환한 각 경로의 본문 크기를 집계하고, 같은 파일의 별칭도 각각 계산해 동일 본문 반복을 보고합니다. 경고는 **지침 탐색 → 최근 적용 지침 · 스킬**과 CLI 기록에서 확인할 수 있습니다. 이미 자동 적용된 파일은 변경 확인이 필요한 경우에만 다시 읽도록 안내합니다. ‘필요할 때 읽기’는 모델이 조건을 판단해 원문을 여는 방식으로, 실제 열람 여부는 실행 기록에서 확인해야 합니다.

프로젝트 루트의 `AGENTS.md`에는 TARS 전용 규칙과 이 절을 읽는 조건만 둡니다. 개인 공통 규칙을 복제하거나 모든 하위 지침·문서를 선제적으로 읽도록 하지 않습니다. 이 구조는 초기 지침과 반복 읽기를 줄이며, 작업 중 대화와 도구 출력까지 무제한으로 억제하는 기능은 아닙니다. [공식 AGENTS.md 로딩 규칙](https://learn.chatgpt.com/docs/agent-configuration/agents-md)과 [스킬의 단계적 로딩](https://learn.chatgpt.com/docs/build-skills)을 참고했습니다.

TARS 작업용 App Server 프로세스에만 `project_root_markers = [".tars-root"]`와 지침 크기 한도를 설정합니다. 계정 전역 설정 파일은 수정하지 않습니다. Codex는 공용 → 부서 → 개인 → 등록 프로젝트 지침 → 소스 프로젝트 지침 순으로 탐색합니다. 기존 프로젝트 `AGENTS.md`, `AGENTS.override.md`, 스킬은 보존하며 TARS가 만든 스킬 링크만 결과 패치에서 제외합니다. 공용·개인 지침을 가리는 override나 기존 스킬 경로와의 충돌은 덮어쓰지 않고 오류로 표시합니다.

기존 Codex 작업 공간은 다음 작업 실행 준비 때 담당 AI의 경로로 이동합니다. Git worktree는 `git worktree move`로 옮겨 미커밋 변경을 유지합니다. 이동 대상이 이미 있거나 이동할 수 없으면 기존 파일을 유지하고 오류를 표시합니다. 백엔드를 재시작하는 것만으로 모든 작업 공간을 일괄 이동하지 않습니다.

스킬은 실제 실행 `cwd`의 `.agents/skills/tars-<id>`에서 원본 폴더 전체로 연결합니다. 프로젝트의 `.agents` 또는 `.agents/skills`가 같은 작업 공간 안의 디렉토리를 가리키는 심볼릭 링크이면 기존 연결을 유지합니다. 외부 경로·끊어진 링크·일반 파일과의 충돌은 오류로 표시합니다. TARS가 추가한 스킬 링크는 실제 대상 디렉토리의 상대 경로로 기록하여 Git 결과 패치에서 제외하고, 프로젝트 자체 스킬 변경은 유지합니다. `skills/list(forceReload: true)`를 먼저 호출하고 thread를 시작·재개한 뒤 `instructionSources`와 탐색 결과를 대조합니다. 설치된 Codex가 `instructionSources`를 제공하지 않거나 필수 파일·스킬이 누락되면 모델 턴을 시작하지 않습니다. 이 API와 루트 탐색 설정의 설치 버전 호환성은 실제 실행으로 검증하지 않았습니다. [공식 App Server](https://learn.chatgpt.com/docs/app-server), [루트 탐색 설정](https://learn.chatgpt.com/docs/config-file/config-advanced#project-root-detection), [스킬 탐색](https://learn.chatgpt.com/docs/build-skills)을 기준으로 구현했습니다.

**문서 & 스킬 → 지침 탐색**에서 공통 자료, TARS, 부서별 팀장·팀원을 트리로 펼칠 수 있습니다. `instructions.md`, `AGENTS.md`, `CLAUDE.md`, 프로필, 공용 스킬과 문서를 선택하면 실제 생성된 파일의 Markdown 미리보기·원문·경로·연결 대상이 표시됩니다. 팀원·파일·문서 이름으로 검색할 수 있고, 프로필 설정과 문서 편집은 기존 화면으로 연결합니다. 기존 문서 카드는 **문서 목록** 탭에 있습니다. 탐색 API는 등록된 관리 파일만 읽으며 프로젝트 소스에 파일을 생성하지 않습니다. 파일이 없으면 안내하며 자동으로 재생성하지 않습니다. 새 API 반영에는 백엔드 재시작이 필요하고, 테스트·빌드·실행 검증은 수행하지 않았습니다.

각 AI의 **공용 지침**, 프로젝트별 지침과 **최근 적용 지침 · 스킬**에서 상속 관계 및 가장 최근에 로딩을 확인한 실행의 결과를 볼 수 있습니다. 발견된 스킬 목록은 실제 사용 기록과 구분합니다. 현재 파일의 변경 내용과 지난 세션의 로딩 기록은 다를 수 있습니다.

데이터 위치는 `TARS_DATA_DIR`로 바꿀 수 있습니다. `.tars-data`와 `.tars-run`은 Git에서 제외합니다. 프로필은 세션 종료 후에도 유지됩니다. 문서의 이전 버전도 저장합니다.

## 업무 이력과 관리자 상태 조회

각 실행에 **받은 지시 → 배정 task → 수행 결과 → 상태 변경**을 연결해 보관합니다. 실행 시작 때 담당자·관리자·지시자, 요청 본문, task 제목·설명·완료 기준과 참조 문서 버전을 저장하므로 이후 task나 프로필을 수정해도 당시 기록은 유지됩니다. 팀장이 생성한 task에는 원본 협의 세션을 연결하며, 기존 task의 문서에서 찾은 협의는 참조 관계로 구분합니다. 실행 중 추가 지시도 기록합니다.

- **작업 상세 → 실행별 업무 기록**: 재실행을 포함한 모든 시도를 선택하고 해당 시점의 지시와 결과를 봅니다. 작업 수정·배정·대기·실행·검토·완료·취소·통합 이력도 확인합니다.
- **실행 기록 → 지시 · 결과 · 상태 이력**: 받은 지시, 상위 협의, 실행 결과, 마지막 실행 이벤트 시각과 상태 변경을 확인합니다. 종료된 실행은 **기록 MD**로 내려받을 수 있습니다.
- 실행 결과는 검토 대기로 제출되고 팀장 검토가 예약됩니다. AI 실행 종료, 결과 검토 통과, 원본 통합은 별도 상태입니다. 오류·취소·서버 재시작 중단은 자동 재실행하지 않으며, 팀장이 명시적으로 보완을 요청한 작업은 설정한 횟수까지 실행합니다.

SQLite의 `work_history` 테이블은 상태와 같은 트랜잭션에서 이력을 추가합니다. 최근 500개 활동 알림과 분리해 보관하고, 이력은 50건씩 조회합니다. 응답의 글자 단위 변화와 서버 확인 신호를 모두 이력 행으로 쌓지는 않습니다. 적용 이전에 저장하지 않았던 지시 사본·과거 상태 변경은 만들어내지 않습니다.

실행 종료 후 `.tars-data/sessions/<실행 ID>/work-record.md`에 지시·task·결과·생성 산출물과 최근 상태 이력을 남깁니다. 전체 변경 이력은 DB에 보존합니다. MD 파일 저장에 실패해도 DB의 요청·결과·이력은 유지하며 화면에서 파일 저장 오류를 표시합니다.

팀장·TARS 프롬프트에는 담당 조직의 인원·작업 개수와 상태 파일 경로를 전달합니다. 현재 실행 여부·담당 작업·진행 보고는 필요한 시점에 조회합니다. 개인 지침 디렉토리의 `team-status.json`도 상태 변경에 따라 갱신하므로 이미 실행 중인 관리자가 필요할 때 다시 읽을 수 있습니다. 팀장은 같은 부서의 팀원을, TARS는 전체 조직을 조회합니다. 프로젝트를 좁혀 보고하더라도 팀원이 다른 프로젝트에서 일하는지는 표시합니다.

`heartbeatAt`은 15초 간격의 **실행 감독 서버 확인**, `lastActivityAt`은 **마지막 AI 실행 이벤트 수신**입니다. 서버 확인이 45초 넘게 오래되면 확인 지연으로 표시하고 자동으로 완료·유휴 처리하지 않습니다. 파일을 읽는 관리자는 파일의 `capturedAt`도 확인합니다. 이력 저장과 상태 파일 갱신 자체는 AI를 호출하지 않으며, 관리자 프롬프트에는 최대 10,000자의 요약과 상세 기록 경로만 추가합니다. 결과 제출 시에는 별도 영속 대기열이 팀장 검토를 예약하며, 보완 판정과 요청별 최종 보고를 다음 실행으로 연결합니다. 상태 파일 갱신만으로는 AI를 호출하지 않습니다.

조회 API는 `/api/{sessions,tasks,members}/:id/history?limit=50&before=<순번>`, `/api/sessions/:id/record`, `/api/members/:id/management`입니다. `before`를 생략하면 최신 이력을 반환합니다. 상태 파일은 전체 담당 조직을, 관리 API의 선택적인 `projectId`는 해당 프로젝트 작업을 대상으로 합니다.

변경 반영에는 백엔드 재시작이 필요합니다. 이력 저장·보존·페이지 조회·상태 범위·상태 파일·재시작 복구 단위 검사 7개와 프런트엔드 빌드가 통과했습니다. 단위 검사는 임시 데이터 디렉토리를 사용했으며 실제 AI·계정·운영 DB를 호출하지 않았습니다. 실행 명령은 `node backend/test/work-history.test.js`, `npm run build --workspace frontend`입니다. 실제 AI 실행 및 브라우저 조작은 별도로 확인해야 합니다.

## 현재 검증 상태와 후속 범위

- 의존성 설치 완료. 설치 시 lifecycle script 실행은 생략했습니다.
- 소스 파일을 읽으며 인터페이스와 흐름을 검토했습니다.
- 초기 구현은 실행 검증 없이 작성했습니다. 이번 변경의 프런트엔드 빌드, 요청 흐름 검사 3개, 에이전트 접근 검사 2개와 업무 자동화 검사 16개를 통과했습니다. 서버 기동·브라우저 조작·실제 AI 호출은 수행하지 않았습니다.
- 화면 및 CLI 이벤트 파서의 실제 호환성은 미검증입니다. 설치된 CLI 버전이나 모델에서 지원하지 않는 옵션은 세션 오류로 표시하도록 구현했습니다.
- 부서별 팀장은 현재 1명입니다. 결과 제출 후 팀장 자동 검토와 제한된 자동 보완은 연결되어 있습니다. 설계 사양의 별도 AI 검토, 여러 부서 간 자동 위임, 자동 병합·충돌 해소와 누적 예산 제한은 후속 범위입니다.
- 팀원의 후속 작업 제안은 결과 보고에 남깁니다. 팀장은 결과 보고 요청 시 현재 상태를 읽고 보고서를 작성합니다.

전체 요구사항은 [REQUIREMENTS.md](./REQUIREMENTS.md)를 참고하세요.

## 작업 중심 결과·검토·보고

업무는 팀장·CEO가 대화로 목표와 범위를 정리해 등록한 단위이며 `requests`에 보관합니다. 대화 문맥 단위는 `conversations`, 개별 실행 기록은 호환 이름인 `sessions`, 업무의 하위 작업은 `tasks`로 분리합니다. 메시지를 보낼 때마다 업무를 만들지 않습니다.

- CEO·팀장은 `tars_register_work` (`POST /api/requests`)에 제목·목표와 범위·프로젝트를 전달해 등록합니다. 등록 시각, 등록 AI와 원본 대화 실행 ID를 보존합니다. 일반 사용자·팀원 실행은 업무 등록 API를 호출할 수 없습니다.
- 후속 협의에는 기존 `requestId`를 전달하여 현재 대화를 같은 업무에 연결합니다. 업무 제목·원래 지시는 덮어쓰지 않습니다. 문서·하위 작업·팀장 위임도 해당 ID에 연결합니다.
- 팀장 협의 결과는 `work`에 업무 제목·목표와 범위·기존 ID를 명시한 경우에만 업무로 등록합니다. 일반 질문에는 `work: null`, 빈 문서·작업 목록으로 응답합니다.
- 예전에 대화마다 생성했던 요청은 삭제하지 않습니다. 등록 정보도 하위 작업도 없는 항목은 업무 목록·상태 API·관리자 결과 요약에서 제외하고, 실제 작업이 남은 항목은 이전 업무로 표시합니다.
- 업무 화면은 완료된 보고까지 기본 표시하며, 연결된 수행 기록을 시간순으로 열고 최종·차단 보고서를 바로 읽습니다. 일반 대화와 원본 실행 로그는 기존 대화·세션 화면에서 확인합니다.

업무 등록 후 협의안을 제출하고 사용자 승인을 기다립니다. 작업 실행 API와 대기열은 승인한 문서·작업 범위가 현재 내용과 일치하는지 검사합니다. 사용자의 계획만·수정 금지 조건을 유지하며, 하위 작업 실행에는 완료 기준이 필요합니다. 등록만으로 완료 처리하지 않으며, 하위 작업이 없는 업무도 담당 AI의 후속 결과를 보고서로 제출해 사용자 확인을 받습니다.

팀원은 수행 내용, 산출물 경로, 완료 기준별 검증과 근거, 미완료·후속 작업을 구조화한 결과로 제출합니다. 서버는 `taskReports`에 버전을 추가하고 작업 상태와 `workflowJobs` 검토 예약을 하나의 트랜잭션에 저장합니다. 같은 실행의 중복 제출은 한 번만 반영합니다. 작업 상세의 **작업 결과·검토**에서 버전별 보고, 채택된 결과, 판정과 근거를 확인하고 **업무 기록 MD**로 작업 전체 기록을 내려받습니다.

팀장은 제출된 버전의 실제 산출물을 확인하고 검토 통과·보완·차단을 판정합니다. 팀장이 없으면 TARS가 검토하며 작업자 자신은 승인할 수 없습니다. 검토 전후에 작업 지시·참조 문서 버전·선행 작업 결과와 파일 지문을 비교합니다. 변경된 결과는 승인하지 않습니다. Git 패치는 제출 버전별 파일로 보존하고, 일반 작업 폴더와 명시한 산출물은 내용 지문으로 확인합니다. 파일 지문은 실행 환경이나 장비 검증의 성공을 증명하지 않으므로 검토 근거가 별도로 필요합니다.

보완은 같은 작업 아래 새 실행과 새 결과 버전으로 이어집니다. 기본 최대 2회이며 **설정 및 연결**에서 0~5회로 조정합니다. 한도 초과·차단은 담당 관리자의 보고 대상으로 남습니다. 요청의 작업이 모두 종료되면 업무를 등록한 팀장 또는 CEO가 원래 요청과 채택된 결과·검토 근거를 취합해 보고서로 저장합니다. 담당 관리자가 없으면 같은 부서 팀장, 마지막으로 CEO가 보고합니다. 최종·차단 보고는 담당 AI 대화와 업무별 결과에서 확인하고 승인하거나 추가 의견을 남깁니다. 보고서 생성은 사용자 확인 대기이며, 사용자가 결과를 승인해야 업무가 최종 완료됩니다. 보고 중 대상 작업이 바뀌면 오래된 보고를 채택하지 않습니다.

후속 처리 대기열은 최근 활동 알림과 별개로 보존합니다. 실행 전 대기는 재시작 후에도 유지하며, 실행 중 중단된 작업·검토·보고는 명시적인 재개가 필요합니다. 요청 또는 작업을 중지하면 후속 실행과 보고도 멈춥니다. 요청의 대기 중 자동 진행 재개, 차단된 검토·보고의 다시 요청, 작업 다시 실행은 별도 동작입니다. 실행 오류를 자동 보완으로 간주하지 않습니다.

AI 관리 도구의 변경 요청은 현재 실행의 `executionToken`으로 인증합니다. Claude에는 세션별 MCP 환경변수로 전달하며 모델 프롬프트에서 제외합니다. Codex도 thread 시작·재개별 MCP 환경에 전달합니다. 공용 App Server 프로세스에 특정 세션 토큰을 고정하지 않습니다. 서버는 유효한 세션에서 실제 수행자를 확인합니다. 토큰은 공개 상태 응답에 포함하지 않습니다. 결과 검토·보고 실행은 최종 응답으로 판정과 보고를 제출하며, 업무 상태를 직접 변경하지 않습니다. 기존 `/tasks/:id/complete`는 근거 없는 완료 변경을 받지 않고, 직접 검토는 결과 ID와 판정·검증 근거를 `/tasks/:id/reviews`에 제출합니다.

개인 인계 파일은 검토된 작업의 경로 목록으로 생성합니다. 다음 실행에는 같은 프로젝트·부서의 채택된 결과에서 만들어진 인계 문서 목록을 제공합니다. 문서에 출처 작업·결과·검토 ID를 보관하고, 최종 응답 끝부분을 개인 기억으로 잘라 넣지 않습니다. 원본은 SQLite이며 생성된 파일을 직접 수정하지 않습니다.

기존 작업은 저장된 요청·결과를 새 구조에 연결하되 검토를 추정하지 않습니다. 이전 결과는 **검토 기록 없음**으로 표시하고 자동 실행을 시작하지 않습니다. 새 결과 제출 전에는 산출물 버전이 없는 과거 결과를 승인하거나 원본에 통합할 수 없습니다. 적용에는 백엔드 재시작이 필요합니다.

## 사용자 승인·의견과 AI 후속 실행

업무 흐름은 한 줄 요약, 검토된 달성률, 수행 보고율, 작업 상태와 다음 할 일만 기본 표시합니다. 목표별 수량과 승인·문서·실행 기록은 펼쳐서 확인합니다. 목록은 진행 업무를 기본으로 12건씩 표시합니다.

새 업무 등록에는 `acceptance`와 `progressPlan`이 필요합니다. `progressPlan`에는 `summary`(160자), `goal`(240자), `goals`(1~12개)를 작성합니다. 각 목표는 `id`, `title`, `target`, `unit`, `weight`, `acceptance`를 가지며 비중 합계는 100입니다. 팀장은 TASK마다 `goalId`와 `plannedUnits`, 담당자·완료 기준을 정합니다. 목표 수량을 초과하는 배정은 거절합니다.

팀원은 `tars_log_progress`/`tars_block`의 `completedUnits`에 TASK에서 수행한 누적 수량을 보고합니다. UI의 수행 보고율과 달성률을 구분하며, 달성률은 `done`이면서 `acceptedReportId`가 있는 TASK의 수량으로 계산합니다. 목표별 `(검토 완료 수량 / 목표 수량) × 비중`을 합산하고, 미완료 상태가 반올림으로 100%가 되지 않도록 버림 표시합니다. 취소·미배정 단위는 분모에 남으며 재실행은 수행량을 0부터 다시 기록합니다. 전체 목표가 달성되지 않았으면 최종 완료 보고로 전환하지 않습니다.

목표·수량·비중은 `PATCH /api/requests/:id`의 `progressPlan`으로 변경하고 다시 승인을 받습니다. 이미 배정한 목표의 단위·완료 기준 변경과 배정 수량보다 작은 목표는 거절합니다. SQLite에 기본 생성하는 **업무 목표·진행률·UI 작성 규칙** 문서는 JSON 예시와 작성 절차를 담으며 문서 API로 조회·편집할 수 있습니다. 지침 생성기는 이 문서를 조건부 지침으로 연결하고, 사용자가 편집한 본문을 덮어쓰지 않습니다. 업무 화면의 **업무 표시·작성 기준**에서도 확인할 수 있습니다.

- **확인할 일**(`/inbox`), **담당 AI 대화**, **업무 흐름**, **작업 상세의 업무 기록**, **실행 기록**에 협의안·보고서의 버전, 작성 AI, 원래 실행과 승인·의견을 함께 표시합니다. 협의안에는 목표·범위, 문서 본문 및 버전, 담당 작업과 완료 기준의 사본이 들어갑니다.
- **승인하고 진행**은 해당 협의안 버전의 실행을 허용합니다. **의견 보내고 재협의**는 입력한 의견을 원래 작성 AI에게 전달하며, 보완한 협의안은 새 승인 대기 버전으로 남습니다. **결과 승인**은 서버에서 최종 확인만 기록하며 확인 답변용 AI 실행을 만들지 않습니다. 차단 보고에는 **재시도**, **범위 변경**, **업무 중단**을 제공하며, 단순 보고 확인으로 업무를 완료 처리하지 않습니다.
- 배정·완료 기준이 준비된 협의안을 추가 의견 없이 승인하면 서버가 TASK를 즉시 대기열에 등록합니다. 미배정 작업·TASK가 없는 업무·추가 의견이 있으면 원래 관리자에게 후속 처리를 예약합니다. 승인 후속 처리 중에는 이미 대기열에 있던 TASK도 실행하지 않습니다.
- 승인·의견은 `workApprovals`, 후속 실행은 `workflowJobs`에 함께 저장합니다. 같은 응답을 중복 전송해도 실행을 추가하지 않습니다. 새 업무의 기본 서명은 목표·범위·업무 완료 기준·프로젝트·승인 정책·관리자 직접 구현 허용에 적용됩니다. TASK 승인 모드에서는 목록도 서명합니다. 기존 업무는 이전의 엄격한 서명을 유지하며, 업무 설정에서 정책을 바꿀 수 있습니다. 서명 대상이 달라지면 기존 버전은 승인할 수 없습니다. 변경된 내용을 협의할 의견은 보낼 수 있습니다.
- 담당 AI가 바쁘거나 동시 실행 한도에 걸리면 후속 실행이 대기합니다. 승인 대기 중에는 모델을 실행해 두지 않습니다. 재시작으로 중단된 후속 실행은 실패 사유와 다시 요청 버튼을 표시하고 자동 재실행하지 않습니다.
- 후속 TARS 실행에는 원래 실행 ID를 `continuationOf`로 보존합니다. 원래 세션의 제공사·계정·프로젝트·작업 경로를 유지해 Codex thread 또는 Claude session을 재개합니다. 재개 실패 시 오류를 표시하며, 사용자가 승인 후속 처리를 명시적으로 재시도하면 원래 협의·보고 사본과 사용자 의견을 전달하는 새 세션을 만듭니다. 세션 연결 실패 후 사용자가 다시 요청하면 이전 실패 시도의 결과도 함께 전달합니다. 기존 실행 기록을 덮어쓰지 않습니다.
- 기존에 저장된 정상 종료 협의안·보고서도 확인할 수 있습니다. 이관 항목은 이전 기록으로 표시하고 과거 승인·검토를 만들어내지 않습니다. 실행 대기·수행·검토 중인 기존 업무는 이관으로 중단하지 않습니다.
- 상태 흐름: `협의 승인 대기 → 승인 후 진행 → 결과 확인 대기 → 사용자 확인 완료`. 의견을 보내면 `의견 반영 중`을 거쳐 새 협의안 또는 보고서 확인 대기로 돌아갑니다.
